# 测试与门禁规范（TESTING-STANDARD）

- 状态：**v5**（2026-09-27 立「交付动作边界」；v4 修正文档自相矛盾；v3 立门禁维护法）
- 红线：**本地不执行仓内代码。** 验证只在 GitHub Actions；**CI 跑通才算通**。

---

## 1. 为什么验证只发生在 CI

本机（Android/bionic、`/tmp` 只读、无 Android SDK/JDK/Gradle）与 CI runner **不是同一环境**。
本地跑出来的"绿"或"红"都不代表发布环境，只会制造错误信心。真实验证必须以 CI 结果为准。

## 2. 红线（与代码一致）

**禁止**在本地执行任何会让**仓内代码运行**的命令，包括：

- `node test/*.js`、`node --check`、`npm test` / `npm run *`
- `./gradlew *`、gradle、任何编译 / 打包
- 直接执行仓库内脚本（`scripts/*.js|sh|py`、`container/engine/bin/*`）做**自检或生成**
- 任何形式的"我先本地试一下"

> 判据：**是否让仓内代码运行**。跑 = 违规；只看 / 只改 = 允许。
>
> 注意：静态校验脚本（`scripts/validate-workflow.py`）与 `node --check` 同样在禁止之列 ——
> 它们由 **CI 的第一步**代为执行（`ci.yml`、`fast-apk.yml`、`build-apk.yml` 都有该步骤），
> 本地不必也不能跑。（此前 `contributing.md` 曾要求本地跑它们，与本规范冲突；v4 已统一。）

## 3. 机制强制

- `scripts/require-ci.js`：非 CI 环境（无 `CI` 环境变量）直接拒绝，退出码 **86**
  （与"测试失败 = 1"刻意区分：这是**策略拒绝**，不是结果红）。
- 已接入的入口：
  - `container/engine` 的 `test` / `test:logic`（`container/engine/package.json`）；
  - `kernel` 的**全部**测试 —— 守卫写在每个测试都会 `--require` 的 `kernel/test/_preload.js`，
    因此**直接调用单个测试文件也拦得住**。
- 未接入守卫的脚本（如 `validate-workflow.py`）不靠机制拦截，靠本规范约束；它们只在 CI 运行。

## 4. 允许的本地操作（白名单）

- 编辑文件（write / edit）
- 只读检查：`read` / `grep` / `glob` / `ls` / 统计
- 提交与推送（经 API 或 tag 通道）
- **对账的"报告模式"**（只列事实、不做断言）—— 它不是测试

## 5. 唯一合法验证通道

```
编辑（可连续多文件） → 一次提交 → 推分支/PR → CI 执行 → 读 CI 结果 → 修复 → 再推
```

读取 CI 结果的两条通道：

1. **API**：`GET /actions/runs/{id}`、`/jobs`、`/jobs/{job_id}/logs`
2. **admin 回执通道**：`git push origin refs/tags/admin-<cmd>` → 结果写 `ci-admin` 分支

> **批次提交**：本地允许连续编辑多个文件，攒成一个逻辑单元后再推 —— 推送是"交付"，
> 不是"验证"。不要每改一个文件推一次（详见 [contributing.md](../runbook/contributing.md) §2）。

## 6. 门禁归属

所有门禁（目录对账、dead-path、原生资产一致性、分层依赖、契约 schema、桥协议、OTA、
跨层版本校验）**只作为 CI 步骤存在**。

## 7. 门禁法（门禁不许长成第二套源码）

背景：2026-09-26 全量审计，测试/门禁约 14,500 行 ≈ 源码的 42%。总量可控，但三类门禁的
**边际维护成本**在制造"双向开发"税：多副本判据、钉字面量/文件名的扫描、需要人记得同步的手维护清单。
以下四条约束所有**新增或整改**的门禁；行为回归与防复活绊线是资产不是负债。

1. **一判据一实现**：门禁逻辑住 `scripts/`（先例：`verify-runtime-elf.sh`），workflow 只准调用。
2. **判据数据化，清单禁手维护**：优先"数据格子 + 唯一执行器"（先例：`kernel/src/guard/native/supply-table.json`）；
   必须进 git 的清单只能由生成器产出、并被对账门禁核验（先例：`gen-native-assets.js` ↔ `git diff --exit-code`）。
3. **扫描式门禁限额 + 自证**：绊线类门禁 ≤60 行，必须带违例样本自证。
4. **门禁预算制（一进一退）**：净增 >100 行的门禁 PR，必须同时退役或合并 ≥ 等量的重叠覆盖门禁。

## 9. 交付动作的边界（agent 只推送；安装/重启由人决定）

2026-09-27 立规。起因是一次真实的越界：agent 在一天内连推 4 个内核版本 + 7 个壳版本，
并**每一步都请用户装一次 APK 回报读数**。而 Android 的规则是**覆盖安装必杀 App 进程**，
于是会话被连环打断；agent 还据此误判成"内核升级导致重启"（实际内核 OTA 在 `:node` spawn 前
完成升级，**不触发任何重启**）。

**分工（硬边界）：**

| 谁 | 做什么 |
|---|---|
| agent | 改代码、推 `main`、让 CI 出产物（APK / 内核 OTA 包）、读日志与设备只读状态 |
| **人** | **决定何时安装、何时重启**；agent 不得以验证为名要求反复装机 |

**三条操作纪律：**

1. **攒批**：能并进同一个包的改动先合并，**一次安装覆盖多件事**；不许"一改一发一装"。
2. **内核侧改动不需要人做任何动作**：下次自然启动即生效（OTA 自动更新是保命链路，必须始终完整）。
3. **只有"非上机不可验"的判据才来请人**，且一次说清：这次装能验完哪几条、还剩哪几条等下一批。

**推论（别把结论建在错误的因果上）**：设备上"App 消失了"优先怀疑**装机动作**（L0 覆盖安装），
而不是内核 OTA —— 后者的正确性判据是 `diagnostics` 里的 `kernel-ota: 启动自动升级内核到 <版本>`。
